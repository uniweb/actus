# The 2.0 docket

**Owner:** Diego Macrini

**Status:** CURRENT — 2026-08-30. What a future `2.0` should carry, and why.
⛔ **No `2.0` is planned or scheduled**, and nothing here is a commitment. This doc
exists so that *if* one is ever cut, the decision is made against the whole list
rather than against whichever item prompted it — and so §1 is not rediscovered a
third time.

Companion to [`1.0-freeze-audit.md`](1.0-freeze-audit.md), which records what the
1.0 freeze *reviewed*. This records what it **cost**, which is a different thing and
was not apparent at the time.

---

## 1. The finding — 1.0 froze the data model, not just the names

The `1.0` promise is usually read as *"nothing gets renamed or removed without a
major."* It is stricter than that. **Not one public enum or all-public struct in the
workspace carries `#[non_exhaustive]`**, which means:

- **enums** — adding a variant breaks any downstream exhaustive `match`, so it is a
  major change. (Constructing existing variants stays fine; only matching is
  affected.)
- **structs with no private field** — adding a field breaks any downstream struct
  literal, so it is a major change. Actus's own tests construct `Request` that way,
  which is the natural shape for a middleware unit test in a consumer too.

⇒ In `1.x`, Actus can add **methods and free functions, and essentially nothing
else.** Every extension point in the data model is welded shut until a major.

### Re-run it rather than trusting the list below

The set of frozen types is state-sensitive: mark one type and this doc is stale.
The query is the durable artifact, not its output. From the repo root:

```bash
python3 - <<'PY'
import re, pathlib
enums, structs = [], []
for f in sorted(pathlib.Path("crates").rglob("*.rs")):
    src = f.read_text()
    for m in re.finditer(r"pub (enum|struct) (\w+)\s*\{(.*?)\n\}", src, re.S):
        kind, name, body = m.groups()
        if "#[non_exhaustive]" in src[max(0, m.start() - 300):m.start()]:
            continue
        if kind == "enum":
            enums.append(f"{name}  [{f.name}]")
        else:
            fields = re.findall(r"^\s{4}(pub )?\w+\s*:", body, re.M)
            if fields and all(fields):
                structs.append(f"{name} ({len(fields)} fields)  [{f.name}]")
print("enums - a new VARIANT would be breaking:")
for e in enums: print("  " + e)
print("structs, all-pub - a new FIELD would be breaking:")
for x in structs: print("  " + x)
PY
```

**Measured 2026-08-30: 9 public enums and 9 all-public structs, none marked.**

## 2. What that costs, concretely

| cannot be added in `1.x` | what it blocks |
|---|---|
| a `WebError` variant | any new HTTP error mapping — 409 Conflict, 410 Gone, 422 Unprocessable |
| a **`ParamType`** variant | **any new parameter type** — `Uuid`, `i32`, `Option<T>`, a date |
| a `Verb` variant | `TRACE`, `CONNECT`, anything the spec grows |
| a `ReplyData` variant | any new reply shape |
| a `ParamSource` variant | a header- or cookie-sourced parameter |
| a `ServerError` variant | naming a new class of startup/serve failure |
| a field on `RouteDef` / `ParamDef` | **any new per-route metadata at all** |
| a field on `Request` | any new routing-derived projection (see §4) |

⭐ **`ParamType` is the one that will actually bite.** *"Can I have a `Uuid` path
param?"* is the most predictable request a web framework receives, and today the
honest answer is *"not before 3.0."*

⚠️ **It has already invalidated a shipped design record.**
[`proposals/per-route-body-caps.md`](proposals/per-route-body-caps.md) states that
its Phase 2 "is a purely additive change on top — `RouteDef.max_body` would just add
a new field." That was true when written (2026-05-13, pre-1.0) and became false at
the freeze. A correction note is now on that doc. Two separate proposals in this repo
rested on the same assumption and neither caught it, which is the argument for
recording the constraint here rather than in either of them.

## 3. The sweep a `2.0` should carry

**Mark `#[non_exhaustive]`** — open domains and everything the framework populates:

| type | why |
|---|---|
| `WebError` · `Verb` · `ParamType` · `ParamDefault` · `ParamSource` · `ReplyData` · `ServerError` | the domain is genuinely open-ended (HTTP statuses, methods, types, sources) |
| `Request` · `RouteDef` · `ParamDef` · `RouteMatch` · `RateLimitClass` · `openapi::Options` · `openapi::ServerInfo` | framework-populated: a consumer reads them, it should not be constructing them |
| `ProblemDetails` · `ReplySpec` | already builder-constructed (`ProblemDetails::new(…).detail(…)`, `build_reply()…done()`), so marking costs consumers nothing — and `ProblemDetails` has obvious room to grow (RFC 7807's `type` / `instance`) |
| `Outcome` | cheap — consumers *return* it rather than match on it, so marking costs them nothing |

**Leave alone, and say so in a `///` so nobody re-derives it:**

- **`ControllerMode`** — `Strict` / `Lax` is the entire space. A forced `_ =>` arm
  there is noise, not safety.

⛔ **The attribute is the easy part; the constructors are the work.**
`#[non_exhaustive]` on a struct forbids downstream literal construction, so:

- **`Request` needs a public constructor** — without one, marking it makes middleware
  fixtures unbuildable: a literal is how this workspace's own tests do it
  (`request.rs`, the `req(...)` helper). Scoped 2026-08-30: the production consumer
  constructs **no** `Request` literal anywhere today, so the constructor is a hard
  requirement for Actus's own tests and for any consumer that starts unit-testing
  middleware — not something a consumer already depends on.
- `RouteDef` / `ParamDef` need the same if hand-built fixtures are to stay possible.

**And add the guard, which is the actual fix:**

- ⭐ **`cargo-semver-checks` in CI.** ✅ **Added 2026-08-30** (`ci.yml` `semver` job on every push, `release-type: minor`; `release.sh` runs the exact form with the release type derived from the bump) — it gated the 1.2.0 release, the first additive one after the freeze. The attribute sweep repairs
  the past; only the CI check prevents the next freeze, and it would have caught this
  one before `1.0` shipped — which is why it went in during `1.x`, independent of any
  major, and why this doc can stay short.

## 4. Items queued behind the sweep

Each is blocked *only* by §1; none of them justifies a major on its own.

- **`Request::expects`** — stamping the matched controller's caller-expectation
  label onto the request. ⚠️ **Demoted 2026-08-30 from capability to
  optimisation:** gating on a claim is reachable in `1.x` — `Router::match_controller`
  is already public, and once `Server::router()` ships (route-family Phase 1) a
  middleware reads the label off the matched controller at the cost of one extra
  tree walk per request. The `2.0` field saves that walk and makes the label
  discoverable beside `rate_limit_class`; that is all it buys now — and the walk
  is **measured at 32–93 ns** (2026-08-30, release build, a 50-mount tree shaped like
  the production consumer's, paths of 2–5 segments, `match_controller` +
  `actus_expects()` including the `Arc` clone; re-measure with a loop over
  `Router::match_controller` before believing a different number). The production
  consumer does not pay even that: it enforces the floor in its `prepare` hook,
  which already holds the controller. ⇒ **Not a reason to cut a `2.0`; a
  discoverability nicety to fold in if one is ever cut for something else.** Design:
  [`proposals/route-family-contracts.md`](proposals/route-family-contracts.md)
  § Enforcement. The finding generalises: any "stamp X onto `Request`" whose X is
  a `Controller` trait method is reachable the same way.
- **`RouteDef.max_body`** — per-route body caps, Phase 2 of
  [`proposals/per-route-body-caps.md`](proposals/per-route-body-caps.md).
- **Dropping the pre-inventory projections** — route-family Phase 1 (v2) now ships
  the per-mount inventory itself, additively: `Router::mounts()` returns a
  `#[non_exhaustive]` record (controller, caller expectation, rate-limit class,
  body cap, `prepare` presence), absence-inclusive — so the omission blind spot is
  fixed in `1.x` and new fields land in minors. What is left for a `2.0` is only
  whether `routes()` / `rate_limit_classes()` are dropped in its favour; keeping
  them as documented projections costs nothing, so this may never be a `2.0` item
  at all.

## 5. What a `2.0` should **not** be

⛔ **A grab-bag of every naming regret.** A major themed *"restore extensibility, plus
the one field that needed it"* is coherent, explicable in a single CHANGELOG
paragraph, and cheap for consumers — only exhaustive matches and struct literals
break, which is a small fraction of real code. A major that also sweeps in renames
spends the same migration on far less, and the `1.0` stability promise is young.
Spend it once, on the change that buys back the most future.
